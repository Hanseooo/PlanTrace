## Overview

```
web/ (Next.js, React)          api/ (FastAPI, Python)            Supabase Postgres
 upload, PPA table,     --->   upload, extract, checks,  --->   plans, pages, ppas, zones,
 findings, CCC matrix          ccc, export                      links, findings, ai_cache
                                     |
                                     v
                         llm.py: Gemini API (PDF in, JSON out)
                         fallback: OpenRouter; cached in ai_cache
```

The web app calls the API directly over HTTPS, with CORS. There is no Next.js proxy and no Supabase client in the browser.

## Stack

| Part | Choice | Why |
|---|---|---|
| Frontend | Next.js, shadcn/ui, TanStack Table and Query | Editable tables and the matrix |
| Backend | FastAPI, Pydantic, `uv` | One schema for extraction, checks and API |
| Types across languages | `openapi-typescript` from FastAPI's OpenAPI | Frontend and backend agree on the contract |
| Database | Supabase as plain Postgres, `pg_trgm`, full-text search. No Supabase Auth or auto API | One shared database for dev and demo |
| DB access | psycopg 3, SQL written by hand, numbered `.sql` migrations | Trigram similarity, `tsvector` and arrays are plain SQL. An ORM would need workarounds |
| AI | Gemini (`gemini-flash-latest`, the current Flash model) through LangChain `with_structured_output`, then an OpenRouter model (`openai/gpt-4o-mini`) through `langchain-openai` on failure | Page text in (not the PDF), JSON matching Pydantic models, both providers behind one seam (`llm.py`) |
| Files | PyMuPDF (page text), pandas/openpyxl (Excel in, CCC export out) | Page-level citations |
| Deploy | Vercel (web, root `web/`), Render (api, root `api/`, free tier), both from `main` | Render's free tier sleeps: wake the api 2 minutes before the demo. Vercel needs `NEXT_PUBLIC_API_URL` before the build; Render's `CORS_ORIGINS` must list the Vercel origin |
| Tooling | ruff and pyright (api), ESLint and `tsc` (web), pytest, Playwright | Run by CI on every PR |

**Not used, and why**
- **LangGraph.** The pipeline is linear.
- **Vector DB or pgvector.** Links plus full-text search are enough. An embedding column can be added later.
- **markitdown.** It returns one text for the whole PDF without page breaks (inferred), and citations need page numbers.
- **File storage.** Uploaded files are not kept. Render's free disk does not persist (inferred), and page text covers citations. Deferred item 1 (page images) reopens this.
- **Jev or Laya.** A CCC cell needs a reason and sources, not only a label.
- **Docker** is only one teammate's offline backup database.

## Contract

1. Pydantic models in `api/app/models.py` define every request, response and AI output.
2. FastAPI publishes them as OpenAPI.
3. `openapi-typescript` generates `web/src/lib/api-types.ts`: `cd web && npm run gen:types`.

A model change is a contract change: tell the team, regenerate the types, and update `seed/fixtures/` in the same PR.

**Mock data.** From ticket 01, every endpoint exists. Until its real query lands, an endpoint returns the matching file from `seed/fixtures/`. The web app has no mock mode. It always calls the API.

**Env names** (contract; listed in `.env.example`): `DATABASE_URL`, `GEMINI_API_KEY`, `OPENROUTER_API_KEY`, `CORS_ORIGINS` (comma-separated origins), `TEST_DATABASE_URL` (pytest only, D7) (api); `NEXT_PUBLIC_API_URL` (web).

## Key flows

**Upload and extract (F1)**
1. `POST /plans` checks the file (`%PDF`, 10 MB), the period and that a city is seeded, saves the plan row with status `extracting` and title `"{type} {start}–{end}"`, and returns at once.
2. A FastAPI `BackgroundTask` reads each page's text with PyMuPDF into `pages`, sends that text to `llm.py` under `=== page N ===` markers with the city's barangay names and codes (text in, not the PDF: S2-12), and writes the cleaned PPAs as `draft`. Zones for a CLUP upload are deferred (AC-07).
3. Status becomes `ready` (ready to confirm) or `failed` with a message. A PDF with no text fails with "No text found. Scanned PDFs aren't supported."
4. At startup, any plan still `extracting` becomes `failed` with "Extraction was interrupted. Retry." (S2-15).
5. The web app polls `GET /plans/{id}` every 2 seconds with TanStack Query's `refetchInterval` until the status leaves `extracting`.

The uploaded file is discarded after step 2. The prompt and output model live in `extract/extraction.py`; `app.extract.load_cache` loads the committed LCCAP response under the same key (S2-19), and the committed orphan answers in `seed/ai_cache/orphans.json` under the keys the run computes (S4-15). The demo fallback is a pre-extracted plan that is already `ready`.

**Checks (F3)**
`POST /checks/run` reads only `confirmed` PPAs. Duplicate and zone checks are SQL. Orphan and CCC use SQL to pick candidate pairs, then `llm.py` for the suggestion or the verdict. Every finding stores `page_ids` and starts as `suggested`.

**CCC export (F5)**
`GET /ccc/export` calls `checks/ccc_export.py`. The real CCC sheet layout is unknown (PRD F5), so the layout changes in that one file.

## The LLM seam

`api/app/llm.py` is the only code that calls a model. Callers pass a connection, a prompt, an input string and a Pydantic output model to `call_llm`, and get a validated object back.

- Gemini first, OpenRouter on failure, each with a 90-second timeout. A missing API key counts as that provider failing. `llm.py` calls the two in order itself, not through `.with_fallbacks`, so the error can name both failures.
- `llm.py` validates the raw output against the output model itself.
- Cache: `cache_key()` hashes the primary model id, the prompt, the input and the output model's name. Rows live in `ai_cache`. The key ignores which provider answered, so a row primed while Gemini was down still hits. A hit returns without a network call, so the demo replays offline and teammates share results. The S2-19 loader imports `cache_key()` rather than copying it.
- Only output that passed validation is cached, so a bad answer never replays. The row is written on the caller's connection, and the caller commits.
- When every provider fails, times out or returns invalid output, `LLMError` is raised. Its message names each provider and its reason, for example "Gemini timed out after 90 s; OpenRouter returned invalid JSON.", and never contains a key or a stack trace. Callers turn it into a `failed` status or a message.

## Data model

| Table | Key columns |
|---|---|
| `lgus` | `psgc_code`, name, level |
| `plans` | id, `lgu_psgc`, type, title, period_start, period_end, status (extracting, ready, confirmed, failed), error |
| `pages` | id, plan_id, page_no, text, `tsv` |
| `ppas` | id, plan_id, code, title, description, office, sector, barangays (PSGC[]), cost, year_start, year_end, page_id, status (draft, confirmed), updated_at |
| `zones` | id, plan_id, barangay, zone_type, hazard, forbidden_sectors[], page_id |
| `links` | id, child_ppa_id, parent_ppa_id, source (ai, manual), status (suggested, confirmed, rejected) |
| `findings` | id, check (duplicate, orphan, ccc, zone), ppa_a, ppa_b, verdict, reason, page_ids[], status (suggested, confirmed, rejected), note, created_by (ai, rule), reviewed_at, barangay (PSGC code it is grouped under) |
| `check_runs` | id, ran_at, counts (jsonb, the run's `CheckCount` list) |
| `ai_cache` | key, response, created_at |
| `questions` | id, text, answer, cited_page_ids[], created_at (deferred with F7) |

Every row carries `lgu_psgc` through its plan. Office names, sectors and languages are data, not code. `plans.status` values are settled in `api/app/models.py` (#2): `extracting`, `ready`, `confirmed`, `failed`. "Uploading" is web-only (AC-03). Sector is the D3 list in `models.py`: `housing`, `drainage`, `flood_control`, `roads`, `evacuation`, `agriculture`, `water_supply`, `health`, `education`, `livelihood`, `commercial`, `industrial`.

## API

| Method | Path | Does |
|---|---|---|
| POST | `/plans` | Upload a file with type and period, start extraction |
| GET | `/plans`, `/plans/{id}` | List plans, plan status |
| POST | `/plans/{id}/retry` | Send the file of a `failed` plan again (multipart `file`) and restart extraction; 409 unless `failed` (S2-14) |
| GET, PATCH, POST, DELETE | `/plans/{id}/ppas`, `/ppas/{id}` | Edit the PPA table. POST adds a row (empty body: blank), `draft` in a `ready` plan, `confirmed` in a `confirmed` one; PATCH changes only the fields sent; DELETE answers 204. 422 naming the field for a bad barangay, cost, year or `page_id`; 409 while the plan is `extracting` or `failed`; 404 for an unknown id (S3-03 to S3-07) |
| POST | `/plans/{id}/confirm` | Confirm a plan and all its rows in one transaction; a `confirmed` plan comes back unchanged. 409 "Add a row first" with no rows, 409 while `extracting` or `failed` (S3-08) |
| GET | `/barangays` | The city's barangays (`psgc_code`, `name`) by code, for the barangay picker and names (S3-01) |
| GET | `/pages/{id}` | One page's `plan_id`, `page_no` and text for the source panel; 404 for an unknown page (S3-02) |
| POST | `/checks/run` | Run all 4 checks, store the findings and the run, return its `ran_at` and counts |
| GET | `/checks/latest` | The last run's `ran_at` and counts, or `null` before any run (S4-02) |
| GET, PATCH | `/findings`, `/findings/{id}` | List findings, each with its grouping `barangay`; confirm, reject, note |
| GET | `/ccc`, `/ccc/export` | Matrix data, Excel file |
| GET | `/chain` | Nodes and edges for the chain view (deferred) |
| POST | `/ask` | Question in, cited answer out (deferred) |

`GET /plans` reads the `plans` table (S1-11), so it needs `DATABASE_URL`: without it, or when the database is unreachable, it answers 503 and the plans screen shows its error state with Retry. This changes S0-07, under which the app started and answered without `DATABASE_URL`; the api still starts without it. `GET /plans/{id}` and `GET /plans/{id}/ppas` read the database too (S2-16) and answer 404 for an unknown plan. `GET /barangays` and `GET /pages/{id}` read it too (S3-01, S3-02), with 503 the same way and 404 for an unknown page. The PPA writes and confirm write it (S3-03 to S3-08) and commit before answering. Every other endpoint still serves `seed/fixtures/` until its slice lands. The `/checks` and `/findings` stubs already take a connection (S4-03), so they answer 503 without `DATABASE_URL` too. Routes get their connection from the `get_conn` dependency in `api/app/db/__init__.py`; tests override it with `TEST_DATABASE_URL` (D7).

Web routes: `/` redirects to `/plans`; `/plans` (plans list and upload form), `/plans/[id]` (a plan's PPA table), `/findings` (findings list and side-by-side detail), `/ccc` (CCC matrix and export link).

The schema is `api/app/db/migrations/001_init.sql` (#3); its check constraints use the `models.py` strings. `002_check_runs.sql` (S4-01) adds `check_runs (id, ran_at, counts jsonb)`, one row per run, and `findings.barangay`, the PSGC code a finding is grouped under. `findings."check"` is a reserved word, so quote it in SQL. `pg_trgm` is enabled. The migrate command keeps applied file names in `schema_migrations`.

## Settled in ticket 01

- Test database (D7): pytest reads only `TEST_DATABASE_URL` (a second Supabase project locally, a Postgres service in CI) and skips the database tests when it is unset. The tests drop and recreate its `public` schema.
- Rejected stays rejected (D5): a reviewed finding is kept on re-run while both PPAs' `updated_at` are older than its `reviewed_at`. A trigger sets `ppas.updated_at` to `now()` on every update that does not set `updated_at` itself, so writers never touch it (seed scripts may).
